# 周报生成

## 口径

- 优先使用用户明确给出的时间范围。
- 如果用户使用相对时间，例如“上周”“本周”，先换算成明确日期，并在回复中写出具体范围。
- “上周”默认按当前时区下的自然周处理，即上一个周一到周日。
- 默认作者口径为 `liushengpeng` 或 `shengpeng.liu`。如果用户明确指定其他作者，按用户要求覆盖。

## 检索方式

- 在仓库根目录读取 git 日志，优先使用：

```bash
git log --since='YYYY-MM-DD 00:00:00 +0800' --until='YYYY-MM-DD 00:00:00 +0800' --pretty=format:'%ad%x09%an%x09%ae%x09%s' --date=short
```

- 如果 `git --author` 过滤结果不稳定，改为全量日志后再用 `rg 'liushengpeng|shengpeng\\.liu'` 过滤作者名或邮箱。
- 仅在用户要求时展示 commit hash、文件路径或逐条 commit 明细。

## 归并规则

- 不要逐条复述 commit message，优先按项目任务主题归并成 5 到 8 项。
- 重点突出上周投入最多、最核心的工作项；bug 修复、体验优化、文案调整等零散内容尽量合并到同一项中，只在一列里统一说明。
- 归并时优先识别这些主题：
  - 智能体能力建设
  - QA / Markdown 渲染与交互
  - 错误处理与异常提示
  - 业务流程修复或联调
  - 工程治理与规范修复
- 详情必须基于 commit message 本身，不要编造未出现的业务结果、数据指标或上线结论。
- 当 commit 比较零碎时，用“支持 / 优化 / 修复 / 调整 / 补充”这类措辞概括。

## 输出格式

- 默认使用中文。
- 先用一句话说明统计范围和提交数量。
- 如果本周提交较多，优先把篇幅留给重点投入的 2 到 4 个工作项，其他零散提交合并到一条“其他修复与优化”中统一说明。
- 主体输出为有序列表，每项固定采用下面的格式：

```md
1. 标题：<任务内容>
   详情：<任务内容描述>
```

- 标题保持项目级表达，不要写成具体 commit 原文。
- 详情写成可直接放进周报的完整句子，合并同类提交，避免重复。

## 异常情况

- 如果指定时间范围内没有匹配作者的提交，明确说明“该时间范围内未找到匹配提交”。
- 如果提交主题过于分散，先按影响面最大的主题归并，再保留少量“工程优化/问题修复”兜底项。
