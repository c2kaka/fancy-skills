# 周报生成

## 输入口径

- 优先使用用户明确给出的仓库、时间范围、Git author、项目名、模块名、总工时和工时精度。
- 默认 Git author 为 `Ouyangfan`；用户明确指定时覆盖默认值。过滤作者名和邮箱时忽略大小写，但不要纳入其他作者的提交。
- 将“上周”按当前时区换算为上一个自然周（周一至周日），将“本周”换算为本周一至今天；在回复和文件名中写明具体日期。
- 总工时必须来自用户输入，不要从提交数量、工作日或历史周报猜测。用户未提供时，先询问总工时，再生成 Excel。
- 默认工时精度为 `0.5` 小时；用户指定其他精度时按用户要求。拒绝负数、非数字或无法按指定精度表达的总工时，并请用户修正。

## 收集 Git 证据

1. 对每个目标仓库解析仓库根目录和仓库名；未指定项目名时，以仓库名作为“项目”。
2. 使用半开时间区间 `[开始日 00:00:00, 结束日次日 00:00:00)` 收集提交，至少保留日期、author name、author email、subject、body、hash 和变更文件/增删行统计。
3. 优先让 Git 过滤默认作者：

```bash
git log --regexp-ignore-case --author='Ouyangfan' \
  --since='YYYY-MM-DD 00:00:00 +0800' \
  --until='YYYY-MM-DD 00:00:00 +0800' \
  --pretty=format:'%H%x09%ad%x09%an%x09%ae%x09%s%x09%b' \
  --date=short --numstat
```

其中 `--until` 使用结束日的次日。若 `--author` 结果可疑，读取同区间全量日志，再仅保留 author name 或 email 中大小写不敏感匹配 `Ouyangfan` 的提交。仅在用户要求时展示 hash、文件路径或逐条 commit 明细。

## 归并任务

- 依据 commit subject/body、共同改动路径和变更范围进行语义归并；不要逐条复述 commit，也不要仅靠关键词硬套分类。
- 通常归并为 5–8 项；提交较少时允许更少，提交较多时将低影响的同类修复合并为“其他修复与优化”。
- “任务内容”用项目级短标题；“任务内容描述”用完整中文句子概括实际改动、联调或修复范围。
- 只写 Git 证据能够支持的事实，不编造业务收益、上线状态、验收结果、数据指标或投入时长。
- 从明确的子系统目录、包名或稳定的提交主题推断“模块”；无法可靠判断时留空，不要猜测。
- 同一项目、同一模块的任务排在一起，为 Excel 的纵向合并做准备。

## 按工作量分配工时

1. 为每个归并任务评估相对工作量权重。综合考虑：
   - 变更广度：跨仓库/跨层联调、涉及的子系统与文件范围；
   - 实现深度：新能力或架构调整、完整链路修复、局部缺陷/文档测试；
   - 迭代强度：同一任务下可归并的有效提交数量和持续日期；
   - 风险与验证：契约迁移、兼容性、数据一致性、回归测试等证据。
2. 不把 commit 数或增删行数直接当作工时；它们只作为相对工作量证据。合并提交、格式化、生成文件和机械重命名不得虚增权重。
3. 将总工时换算为精度单位：`总单位 = 总工时 / 精度`。按权重计算每项的原始单位数，先向下取整，再按小数余量从大到小补齐剩余单位（最大余数法）；余量相同时，优先分配给权重更高、证据范围更广的任务。
4. 最终每项工时必须是数值，且满足：
   - 每项工时是指定精度的整数倍；
   - 所有任务工时之和严格等于用户输入的总工时；
   - 不因四舍五入偷偷增加或减少总工时。
5. 若总单位数少于任务数，允许低权重任务为 `0`，并在回复中提示；不要伪造最小工时。若用户不接受 `0`，减少归并项或请用户调整总工时/精度。

## 生成 Excel

- 使用 `spreadsheets` skill 和其规定的 `@oai/artifact-tool` 工作流创建、检查、渲染并导出 `.xlsx`，不要改用其他表格库。
- 优先复用 [scripts/build_weekly_report.mjs](scripts/build_weekly_report.mjs)：按 spreadsheets skill 的要求在任务临时目录建立 bundled `node_modules` 链接，将脚本复制到该目录后执行。输入 JSON 格式如下，`weight` 是归并阶段得到的正数相对权重：

```json
{
  "periodStart": "2026-08-03",
  "periodEnd": "2026-08-09",
  "author": "Ouyangfan",
  "totalHours": "40",
  "precision": "0.5",
  "tasks": [
    {
      "project": "studio-cloud",
      "module": "dbt dag",
      "title": "画布异步执行链路与结果抽屉",
      "description": "基于 Git 证据归并后的完整描述。",
      "weight": 3
    }
  ]
}
```

调用方式：

```bash
node build_weekly_report.mjs --input weekly-report.json --output '<输出目录>/周报_YYYY-MM-DD_YYYY-MM-DD_Ouyangfan.xlsx' --preview '<临时目录>/weekly-report-preview.png'
```

脚本会输出 JSON 校验摘要。必须确认其中 `allocatedHours === totalHours` 且 `formulaErrors` 为空，并目视检查 `--preview` 生成的预览；预览是验收中间产物，不作为最终交付文件。
- 工作表名使用 `周报`。第一行为固定表头，顺序不得改变：

| 项目 | 模块 | 任务内容 | 任务内容描述 | 本周投入工作量 |
| --- | --- | --- | --- | ---: |

- 每个归并任务占一行。“本周投入工作量”写入可计算的数字，不要写成带“小时”后缀的文本。
- 对连续且相同的“项目”纵向合并单元格；在同一项目内，对连续且相同且非空的“模块”纵向合并单元格。不要合并任务、描述或工时列。
- 版式参照用户提供的截图：
  - A1:D1 使用浅蓝底、深蓝加粗文字；E1 使用浅橙底、深蓝加粗文字；
  - 表头水平和垂直居中，正文垂直居中；文本列左对齐并自动换行；工时列使用数值格式；
  - 使用清晰的细边框呈现表格结构，隐藏网格线，冻结首行；不要把截图中的蓝色选区虚线当成表格样式；
  - 建议列宽依次约为 22、20、48、72、16；根据内容适度调整，避免标题、描述和工时被裁切；
  - 按换行后的内容调整行高；合并单元格中的项目和模块保持垂直居中。
- 文件名使用 `周报_YYYY-MM-DD_YYYY-MM-DD_<author>.xlsx`，并保存到 spreadsheets skill 要求的当前任务输出目录。

## 校验与交付

导出前必须完成：

1. 检查表头、任务行、合并区域和数值类型；
2. 用公式或独立计算核对工时列合计等于用户输入的总工时；
3. 扫描公式错误；
4. 渲染整个工作表并目视检查表头、列宽、换行、行高、边框和合并单元格，修复裁切或错位后再导出；
5. 最终回复简要说明日期范围、匹配提交数、任务数、总工时和默认/实际 author，并提供 `.xlsx` 文件链接。对话中可以附任务摘要，但 Excel 是默认交付物。

## 异常情况

- 指定时间范围内没有匹配作者的提交时，明确说明“该时间范围内未找到匹配提交”，不要生成虚构任务或分配工时；仅在用户明确要求时生成空模板。
- 仓库不是 Git 仓库、日期无效、author 过滤歧义或 Git 日志读取失败时，报告具体问题，不要吞掉错误或继续生成貌似完整的周报。
